# Phase 3 核心知识库工作台总设计

Phase 3 不再按零散控件推进，而是交付一个完整的“核心知识库工作台”主链路：登录后选择团队，上传资料，查看文件处理状态，在当前团队内搜索资料，管理文件基础状态。

## 用户主链路

1. 用户邮箱密码登录。
2. 用户选择或创建团队。
3. 用户上传 PDF/DOCX。
4. 上传后文件进入团队资料列表。
5. 用户查看文件处理状态和状态摘要。
6. 用户搜索当前团队资料。
7. 用户查看搜索结果的文件名、片段和来源。
8. 用户可以软删除文件。
9. 失败文件可以触发重新处理。

## 范围

- 团队工作台首页。
- PDF/DOCX 单文件上传。
- 文件列表、状态摘要、最后刷新时间。
- 当前团队搜索入口。
- 搜索结果列表。
- 文件软删除。
- 失败版本重试。
- 全部关键路径的加载、空状态和错误状态。

## 非范围

- 不做实时订阅。
- 不做自动轮询。
- 不做文件预览。
- 不做原文件下载。
- 不做批量上传。
- 不做文件夹监听。
- 不做 iOS 分享扩展消费。
- 不做成员邀请或权限管理。
- 不做 AI 总结或问答。

## 架构

客户端继续使用小服务 + Hook + 组件的边界：

- `auth/` 负责当前设备登录、注册和退出。
- `workspaces/` 负责团队列表和创建。
- `uploads/` 负责上传校验、checksum、Storage 上传和完成标记。
- `files/` 负责文件列表、软删除、失败重试、状态摘要。
- `search/` 负责搜索 RPC 调用、查询校验和结果映射。
- `components/` 只负责 UI，不直接持有 Supabase 细节。

## 搜索实现边界

后端 RPC `search_workspace_files` 要求 384 维 query embedding、query tokens、query text、filters 和 limit。当前客户端暂不引入浏览器端 E5 模型，Phase 3 工作台先使用确定性 384 维中性向量加词法 tokens 调用 RPC，保证搜索入口、权限边界、结果 UI 和错误处理先贯通。

后续如果需要真实语义搜索，可以把 `SearchService` 中的 query vector provider 替换成浏览器端或后端生成的 E5 embedding，不改 UI。

## 文件操作

- 软删除调用 `soft_delete_file(p_file_id)`。
- 失败重试调用 `retry_file_version(p_version_id)`。
- 两个操作成功后刷新文件列表。
- 软删除必须有确认步骤。
- 只有当前版本状态为 `failed` 且有当前版本 ID 时展示重试入口。

## 验收标准

- 登录后能选择/创建团队。
- 已选团队能上传 PDF/DOCX。
- 上传成功或 duplicate 后刷新文件列表。
- 文件列表显示文件名、状态、大小、更新时间。
- 状态摘要显示文件总数、待处理、可搜索、失败和最后刷新时间。
- 当前团队搜索能提交查询并展示结果。
- 搜索空结果、错误、加载状态可见。
- 文件可软删除，删除成功后列表刷新。
- failed 文件可重新处理，成功后列表刷新。
- 客户端单测、typecheck、build 通过。
