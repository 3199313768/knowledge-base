# 团队知识库 App 设计规范

- 初稿日期：2026-08-04
- 冻结日期：2026-08-07
- 状态：首版产品规范已冻结（用户逐项确认）
- 首版平台：macOS 14+、iOS 17+
- 首版用户：2～10 人的小团队
- 技术方向：Tauri 2、React、TypeScript、Supabase

本文件是首版范围、交互规则和验收门禁的基准。后续若要增加 AI 问答、旧版 Office 格式、复杂权限或其他明确排除项，必须先重新评审产品规范，不得在实施阶段静默扩展范围。

## 1. 产品目标

团队资料分散在成员电脑、聊天工具、网盘和网页中，用户经常知道某份资料存在，却无法快速找到它。

首版产品让团队成员在 Mac 和 iPhone 上集中导入资料，并用自然语言描述需求。系统返回最相关的文件、命中内容片段和来源位置，不直接生成 AI 答案。

核心用户故事：

> 作为团队成员，我输入“去年给客户的报价方案”，能够在几秒内看到正确文件、相关内容片段及其页码，并打开原始文件核对。

## 2. 首版成功标准

首版以单个团队约 5,000 个文件作为性能验证规模，不将其宣传为无限容量：

- 2～10 名成员能够在 Mac 或 iPhone 完成资料导入。
- PDF、DOCX、PPTX、XLSX、JPG/JPEG、PNG、HEIC、扫描型 PDF 和网页能够保存、处理并进入搜索。
- 使用 30～50 个真实问题建立评测集，至少 80% 的问题能在前五条结果中找到预先标记的正确文件。
- 搜索结果必须展示真实来源片段，并提供页码、幻灯片页数、工作表或其他可定位信息。
- 在 5,000 个文件的目标数据量下，搜索请求的第 95 百分位响应时间不超过约 2 秒，不包含客户端网络异常和首次模型冷启动。
- 单个文件处理失败不会阻塞其他文件。
- 不同团队之间的数据、文本片段和搜索结果完全隔离。

## 3. 首版范围

### 3.1 账号与团队

- 使用邮箱和密码登录、注册。首版不提供忘记密码。
- 登录会话在 Mac 和 iPhone 分别保存；退出登录只退出当前设备。
- 一个账号可以创建或加入多个团队；用户必须选择当前团队，所有文件、搜索、成员和通知操作都只作用于当前团队。
- 已登录用户可以创建多个团队，创建者自动成为管理员；团队名称不要求全局唯一。
- 管理员通过邮箱邀请成员，邀请 7 天有效；被邀请人必须使用同一邮箱登录并主动接受。
- 同一团队、同一邮箱只能有一条有效邀请；重新发送会使旧邀请失效，管理员可以撤销未接受的邀请。
- 已是团队成员时再次接受邀请不得重复创建成员关系；首版不支持公开邀请链接或批量邀请。
- 仅设置“管理员”和“普通成员”两种角色。
- 管理员可以邀请、移除、升级或降级成员，也可以修改团队名称和管理团队内全部文件。
- 团队必须始终保留至少一名管理员；最后一名管理员不能退出、降级自己或被移除。
- 普通成员可以上传、搜索、查看和下载当前团队的全部资料，但只能更新或删除自己上传的文件。
- 成员被移除后立即失去该团队全部权限；其此前上传的文件继续归团队所有，由管理员管理。
- 首版不提供删除整个团队的入口；内测期确需删除时走人工运维流程并记录审计事件。
- 首版不提供文件级权限。

### 3.2 资料导入

- Mac 支持拖拽和批量选择文件。
- 每台 Mac、每个团队最多配置一个监听文件夹，递归发现受支持的新文件和内容变化。
- 本地完整路径和目录结构不上传；本地删除、移动或重命名不会自动修改云端资料。
- 用户可以暂停监听或更换文件夹；更换后不影响已经上传的云端资料。
- iPhone 支持从系统分享菜单导入文件、图片和网页链接。
- iPhone 分享扩展先把待上传内容写入 App Group 共享队列，再由主 App 或系统允许的后台任务上传，避免在扩展的短生命周期内执行大文件处理。
- 客户端展示“等待上传、上传中、等待处理、处理中、可搜索、部分可搜索、处理失败”等状态。
- 团队内发现相同内容校验值时不重复上传；手动上传时由用户选择跳过，或在具备管理权限时明确作为已有文件的新版本。
- 不能仅因文件名相同自动覆盖已有文件。Mac 文件夹监听遇到相同校验值时自动跳过；同一路径内容变化时创建新版本。
- 新版本处理成功前继续使用旧版本；成功后原子切换。处理失败时保留旧版本。
- 首版不展示历史版本，也不提供版本回退。
- 删除文件前必须二次确认；确认后立即从资料列表和搜索中隐藏，再由后台异步清理原文件与索引。
- 单文件默认上限为 100 MB。

### 3.3 内容处理

- 首版支持 PDF、DOCX、PPTX、XLSX、JPG/JPEG、PNG、HEIC 和网页 URL；不支持旧版 DOC、PPT、XLS。
- PDF、DOCX、PPTX、XLSX 和网页提取正文与可定位结构。
- JPG/JPEG、PNG、HEIC 和扫描型 PDF 使用 OCR 提取文字。
- 原生文字 PDF 不执行 OCR。
- 网页采用导入时快照：保存当时可读取的标题、正文和原始 URL，不自动同步后续变化，也不保存完整视觉样式、视频或交互内容。遇到登录、验证码、付费墙或访问限制时标记处理失败，不尝试绕过。
- 长内容按照自然段、页面、幻灯片或工作表等边界切分；每个片段保留来源位置。
- 文本片段生成语义向量并写入 PostgreSQL/pgvector。
- 处理任务异步执行，并支持自动重试和人工重新处理。

### 3.4 搜索与查看

- 默认首页采用“搜索工作台”结构。
- Mac 使用“导航—搜索结果—文件预览”三栏布局。
- iPhone 使用搜索优先的单栏结果列表。
- “全部资料”作为侧边栏中的次级页面，采用类似 Finder 的分类和列表结构。
- 自然语言语义搜索与文件名、正文关键词检索同时执行。
- 系统先按团队权限限定候选内容，再执行排序。
- 同一文件命中的多个文本片段聚合为一个文件结果。
- 每条结果展示文件名、文件类型、上传者、更新时间、命中片段和来源位置。
- 支持按文件类型、上传者和日期筛选。
- 支持在线预览；无法预览时调用系统应用打开原文件。
- 搜不到时明确提示调整关键词或筛选条件，不生成、猜测或编造答案。
- 首版不生成 AI 答案、摘要或内容改写，也不提供聊天式追问。

### 3.5 同步与通知

- Mac 和 iPhone 使用同一云端资料和处理状态。
- 网络中断时，客户端保留待上传任务；恢复后继续上传或重试。成员失去团队权限后，对应队列停止上传。
- 团队邀请通过邮件发送。
- 上传者在文件处理完成、部分完成或最终失败时收到系统通知；上传成功、处理中和自动重试不发送系统通知。
- 已授权系统通知时发送 Mac/iPhone 通知，同时在 App 内保留处理状态。
- 成员被移除后不再收到该团队通知。
- Mac 文件夹监听对连续文件事件进行防抖，并在计算校验值后决定是否上传，避免同一修改产生大量重复任务。
- 首版不提供通知偏好配置、管理员通知中心或全员广播。

## 4. 首版明确不做

- 在线编辑 Word、PPT 等原始文件。
- AI 直接回答、总结或生成内容。
- 评论、多人实时协作和审批流。
- 企业微信、飞书、钉钉或第三方网盘自动连接器。
- Windows 和 Android 客户端。
- 复杂角色、部门权限和文件级权限。
- 完整离线知识库。
- 用户可见的文件版本历史。
- 用户可见的回收站。
- 团队自助删除。
- 旧版 DOC、PPT、XLS 文件解析。
- 自动标签、知识图谱、公开发布和订阅。
- 付费、套餐和公开应用商店发布。

`FILE_VERSION` 和内部软删除标记只用于安全更新、重试和后台清理，不形成面向用户的版本历史或回收站功能。

## 5. 总体架构

系统由三个独立边界组成：

1. **Tauri 客户端**：React 界面、共享业务逻辑，以及 Rust/Swift 系统桥接。
2. **Supabase 云端底座**：认证、团队权限、PostgreSQL、对象存储和搜索函数。
3. **文件处理服务**：任务调度、文件解析、OCR、文本切分、向量生成和状态通知。

客户端不执行服务端文件解析，也不持有 Service Role。文件处理服务不包含界面逻辑。搜索的权限过滤由数据库规则和查询函数共同保证，而不是由客户端隐藏结果。

### 5.1 客户端模块

- **React UI**：登录、搜索、资料列表、预览、上传队列和成员管理。
- **领域模块**：上传状态机、重试、去重、搜索请求和结果映射；Mac 与 iPhone 共用。
- **Rust/Swift 桥接**：Mac 文件夹监听、iPhone 分享扩展、系统通知、安全凭证和文件访问。
- **本地持久化**：保存待上传任务、失败重试信息和 Mac 文件夹监听配置。

### 5.2 云端模块

- **Supabase Auth**：登录、会话和邀请流程。
- **PostgreSQL**：团队、成员、文件、处理状态和文本片段。
- **Row Level Security**：以团队成员关系作为数据访问边界。
- **Storage**：保存原始文件，使用短时有效的签名地址访问。
- **搜索函数**：组合全文关键词匹配、向量相似度、元数据过滤和文件聚合。

### 5.3 文件处理服务

- 第一版使用 Node.js/TypeScript 实现任务调度和统一解析接口。
- 每种格式通过独立适配器实现统一的 `extract -> normalized blocks` 契约。
- OCR 和向量模型通过独立接口调用，避免供应商逻辑进入业务层。
- 如果后续某种格式必须使用 Python 工具，只新增独立解析适配器或工作进程，不改变客户端和数据库接口。
- 任务处理必须幂等：同一个 `FILE_VERSION` 被重复投递时，不产生重复片段或重复通知。

## 6. 数据模型

### 6.1 核心实体

| 实体 | 关键字段 | 用途 |
|---|---|---|
| `WORKSPACE` | `id`, `name`, `created_at` | 团队空间 |
| `MEMBERSHIP` | `workspace_id`, `user_id`, `role` | 团队成员和角色 |
| `INVITATION` | `workspace_id`, `email`, `status`, `expires_at` | 团队邀请与撤销 |
| `FILE` | `workspace_id`, `uploader_id`, `current_version_id`, `display_name`, `source_type`, `deleted_at` | 用户看到的逻辑文件 |
| `FILE_VERSION` | `file_id`, `storage_path`, `checksum`, `mime_type`, `size`, `status` | 某次上传的实际内容 |
| `CONTENT_CHUNK` | `version_id`, `content`, `source_location`, `embedding` | 可搜索文本片段及其来源 |
| `PROCESSING_JOB` | `version_id`, `stage`, `status`, `attempts`, `error_code` | 异步处理任务 |
| `DEVICE` | `user_id`, `platform`, `notification_token` | 设备通知注册 |
| `AUDIT_EVENT` | `workspace_id`, `actor_id`, `action`, `target_id`, `created_at` | 敏感操作审计 |

### 6.2 数据规则

- `FILE` 属于一个 `WORKSPACE`，每个 `FILE_VERSION` 只属于一个 `FILE`。
- `MEMBERSHIP` 是用户访问团队数据的唯一授权依据；客户端选择的当前团队不能替代数据库权限判断。
- 每个团队必须至少保留一名管理员。
- 同一团队、同一邮箱最多存在一条有效邀请；单条邀请记录在接受、撤销或过期后不得再次使用，重新邀请必须生成新记录。
- 搜索只查询 `FILE.current_version_id` 对应的片段。
- 新版本成功前继续使用上一个成功版本；新版本完成后原子切换 `current_version_id`。
- `source_location` 统一表示页码、幻灯片、工作表、单元格范围、网页标题和原始 URL 等位置。
- Mac 监听文件夹的完整本地路径不上传云端。
- 删除操作先写入内部墓碑状态并立即从搜索隐藏，再由后台清理原文件、文本片段和向量；首版不提供用户恢复入口。

## 7. 上传与处理流程

1. 客户端创建文件或文件版本记录，状态为“等待上传”。
2. 客户端获取短时签名上传地址，直接把文件写入对象存储。
3. 上传完成后，数据库记录进入“等待处理”，并创建处理任务。
4. 文件处理服务校验真实文件类型、大小和安全规则。
5. 对可直接读取的文档提取文字和结构；对图片或扫描件执行 OCR。
6. 标准化内容并按语义与来源边界切分。
7. 为片段生成向量，写入文本、位置和向量数据。
8. 所有必需阶段成功后，原子切换当前版本并标记“可搜索”。
9. 客户端通过状态订阅或刷新获得结果，系统通知上传者。

## 8. 搜索流程

1. 用户输入自然语言描述和可选筛选条件。
2. 服务端确认用户的团队成员身份。
3. 查询文本生成向量。
4. 在当前团队和当前文件版本内执行向量召回。
5. 同时执行文件名、正文关键词和元数据检索。
6. 合并两路结果，综合语义相似度、关键词命中、文件新鲜度和筛选条件排序。
7. 按文件聚合片段，为每个文件选择最能解释命中的片段。
8. 返回前若干文件，以及片段、来源位置和必要的文件信息。

排序权重必须通过固定评测集调整，不能仅根据主观感受修改。

## 9. 错误处理

- **网络中断**：客户端持久化队列，恢复后续传或重试。
- **权限失效**：成员被移除后，客户端停止对应上传队列并清除该团队的可访问缓存。
- **重复文件事件**：防抖、校验值和幂等键共同去重。
- **格式不支持**：在上传前拒绝并列出首版支持的格式，不创建云端文件记录。
- **文件损坏**：保留已上传的原始文件，展示明确错误，并允许下载或重新处理。
- **加密文件**：标记为需要用户处理，不尝试绕过密码。
- **OCR 或向量生成临时失败**：指数退避重试；超过上限后标记失败并通知上传者。
- **部分页面失败**：成功片段仍可搜索，文件状态为“部分可搜索”，结果中明确提示。
- **新版本处理失败**：继续使用旧的成功版本，不覆盖当前可搜索内容。
- **删除清理失败**：文件已从用户查询和搜索中隐藏，后台任务持续重试物理清理。

## 10. 安全与隐私

- 所有团队数据表执行 Row Level Security。
- 签名下载地址短时有效，不把永久公开地址写入客户端。
- Service Role 只用于可信后台任务和测试数据准备，禁止进入客户端；权限测试必须使用普通用户身份。
- 服务端凭证、OCR 密钥和向量模型密钥只保存在服务端。
- 文件正文、图片和搜索内容不发送给第三方生成式 AI；OCR 和向量生成由受控处理服务完成，优先使用自托管或本地运行的模型。
- 日志只记录团队 ID、文件 ID、任务阶段、耗时和错误码，不记录文件正文、搜索原文、验证码、密钥或临时下载地址。
- 对声明类型与真实内容不一致、超出限制或明显恶意的文件拒绝处理。
- 邀请、成员移除、文件删除等敏感操作记录审计事件。
- 成员被移除后，其会话对该团队数据立即失效。

## 11. 测试策略

### 11.1 单元测试

- 上传与处理状态机。
- 文件校验、去重和版本切换。
- 文本切分与来源位置保留。
- 搜索合并、排序和文件聚合。
- 权限判断和删除清理规则。

### 11.2 固定文件样本

建立包含以下样本的版本化测试集：普通 PDF、扫描 PDF、Word、PPT、多工作表 Excel、中英文图片、网页、空文件、损坏文件、加密文件和超过限制的文件。

每次修改解析器后执行整套样本，防止格式之间产生回归。

### 11.3 集成测试

- 上传到可搜索的完整链路。
- 自动重试和任务幂等。
- 文件更新后的原子版本切换。
- 文件删除后的搜索隐藏与物理清理。
- 跨团队读取、搜索和签名地址访问全部被拒绝。
- 跨团队更新、删除和下载全部被拒绝。
- 普通成员不能更新或删除其他成员上传的文件，管理员可以管理团队内全部文件。
- 最后一名管理员不能退出、降级或被移除。
- 邀请过期、撤销、重复接受和邮箱不匹配均被拒绝。

### 11.4 客户端测试

- Mac 拖拽、批量上传、文件夹监听和重复事件防抖。
- 离线队列持久化、恢复上传和失败重试。
- iPhone 分享扩展在主 App 未启动时保存任务。
- 通知跳转到正确的文件或失败任务。

### 11.5 端到端验收

覆盖以下真实流程：

> 创建团队 → 邀请成员 → 上传资料 → 等待处理 → 自然语言搜索 → 查看命中片段 → 打开原文件。

同时执行跨团队隔离用例。任何权限隔离失败都阻止首版发布。

## 12. 发布策略

1. **开发验证**：使用固定样本和约 100 个非敏感文件验证完整链路。
2. **双人试用**：开发者与一名成员使用真实但不敏感的资料，记录失败文件和“搜不到”的问题。
3. **小团队内测**：扩大到 2～10 人，达到搜索质量、安全和性能门槛后再继续。
4. **稳定分发**：完善客户端签名、崩溃监控、数据库备份和恢复演练。

首版不公开上架。Mac 使用签名的内测构建，iPhone 使用 Apple 提供的内测分发渠道。

## 13. 关键风险与缓解措施

| 风险 | 缓解措施 |
|---|---|
| 不同文件格式解析质量差异大 | 独立解析适配器、固定样本集、部分成功状态 |
| 自然语言搜索看似智能但结果不稳定 | 固定真实问题评测集、混合检索、按文件聚合、持续记录搜不到案例 |
| Tauri 与 iOS 分享扩展集成复杂 | 首个技术验证只实现分享扩展写入 App Group 队列，再开始完整客户端开发 |
| Mac 文件监听产生重复或冲突 | 防抖、校验值、幂等键和版本原子切换 |
| 后台处理成本失控 | 只对扫描内容使用 OCR、限制文件大小、记录每阶段耗时和调用量 |
| 权限配置错误导致资料泄漏 | 数据库层 RLS、跨团队集成测试、发布前安全门禁 |

## 14. 已完成的技术验证

在正式搭建全部产品功能前，用最小实验验证三个高风险点：

1. 同一套 Tauri 2 + React 工程能够构建并运行 Mac 与 iPhone 客户端。
2. iPhone 分享扩展能够把一个 PDF 写入 App Group 队列，主 App 能读取并上传。
3. 准备约 20 份混合资料，完成解析、向量写入和自然语言搜索，验证正确文件能够出现在前五条。

Phase 0 已取得三项实验的观察证据并裁决为 `GO`。下一步是编写并评审 Phase 1 云端基础与安全边界实施计划；在权限隔离门禁通过前，不导入真实团队资料，也不进入客户端完整功能开发。
